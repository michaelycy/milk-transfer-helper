## NFR-1 医学安全与内容合规 `最高优先级`

- 所有医学类规则默认值（FR-C2 转奶模板、FR-C6 安全规则、FR-E1 预警阈值、FR-D3 大便图卡、FR-F3 奶量参考量、**FR-K1 AI 场景提示词模板**）**上线前须经儿科医生/注册营养师审核**，审核版本与日期留档；阈值调整走配置表并重新走审核。
- 全部输出为"提示与记录工具"，不含诊断、疗效、用药建议；预警与问卷结果固定附免责声明。**AI（模块 K）输出同样受此约束**：便便评估的预警级别一律由 FR-E1 规则引擎裁决，AI 仅产出结构化观察；模型自由文本经输出护栏校验，红线词（诊断/用药/疗效承诺）命中即替换为固定引导文案。
- 内容遵守《广告法》对母乳代用品宣传的限制：不出现品牌推荐/排名/绝对化用语；"我的"页与文章页固定免责声明入口。

**验收标准**
- [ ] 每条医学规则有对应审核记录（顾问、日期、版本）；
- [ ] 全局检索无"治疗/治愈/最有效"等违规表述的构建期检查（文案表 lint）；
- [ ] 红色预警文案不可被配置为"可忽略"。

## NFR-2 隐私与数据合规

- 宝宝数据属敏感个人信息（未成年人）：建档前展示并取得单独同意的隐私政策；
- 数据最小化 + **照片最小化（v2.0-draft5 修订）**：不收集宝宝正面照、真实姓名、精确位置（FR-A1 已约束字段）；模块 K 的拍照能力（FR-K2/K3/K4）遵循「**分析即弃**」默认——照片仅以 base64 随识别请求即时分析、完成即弃不落库；用户显式勾选保留（仅 FR-K3 补录场景）时才上传**私有存储桶**（路径含 user_id、RLS 隔离、注销级联删除），并明确告知用途；`ai_analyses` 只存结构化结果不存照片；
- 支持账号注销与数据级联删除（FR-H2）；用户数据隔离一律依赖 RLS（沿用 `auth.uid()` 模式，新表同规则）；**AI 供应商密钥（v2.0-draft7 修订）**：允许在管理端界面设置，以 AES-256-GCM 加密落库（密钥表无任何客户端授权，密文不下发浏览器），主密钥 `AI_KEY_MASTER_SECRET` 仅存后端环境变量；明文只在后端内存瞬时存在——任何接口响应、日志不回显明文与密文（编辑界面仅见末 4 位掩码）；环境变量密钥仍作为兜底路径。
- **账户与权限合规（v2.0-draft8 增补）**：手机号以「密文 + 哈希指纹」双字段存储、展示一律脱敏、完整值不出后端（FR-H7）；家庭共享遵循**最小披露**——成员间仅互见昵称/头像，退出/移除后个人信息不再披露（FR-H3）；管理端实行固定角色**最小权限（默认拒绝）**与操作审计，审计日志保留 ≥ 180 天且不可改删（FR-J8/J11）；管理端用户查询只输出统计画像并防批量导出（FR-J10）。

**验收标准**
- [ ] 建档流程含单独同意步骤且留痕（同意时间 + 政策版本）；
- [ ] 注销后业务表无残留数据（抽样校验脚本）；
- [ ] 隐私政策变更时重新征集同意；
- [ ] 手机号/成员披露最小化：任何接口响应与页面无完整手机号、无跨成员多余字段（评审抽查）；
- [ ] FR-J11 所列敏感动作逐项留痕，审计表任何角色均无改删授权。

## NFR-3 性能

- 首屏可交互 ≤ 2s（常规网络）；记录提交 P95 ≤ 1s；预警评估在打卡提交后同步完成（用户可即时看到结果）。
- 弱网下提交失败有明确提示与本地草稿保留（不做完整离线同步，见 02-roadmap §2）。

**验收标准**
- [ ] 真机测试报告覆盖低端安卓机型；
- [ ] 记录提交失败时表单数据不丢失（重进可恢复）。

## NFR-4 兼容

- 微信基础库最低版本策略在技术文档中声明并随版本更新；
- iOS 日期解析兼容：**禁止裸 `new Date('YYYY-MM-DD HH:mm')`**，一律复用 `src/utils/date.ts` 的手动解析；
- iPhone SE 小屏与主流安卓分辨率适配。

**验收标准**
- [ ] 构建期 lint 禁止裸日期解析模式；
- [ ] 375×667 小屏下核心页面无截断（设计画板 375×812 基础上验收小屏）。

## NFR-5 可维护性

- 分层不变：`pages → services → supabase`；纯逻辑（计划逐日生成、规则评估、聚合统计）沉淀为 `utils` 纯函数并配单元测试（延续 `date.test.ts`/`chart.test.ts` 模式）。**计划引擎与规则引擎必须有单测覆盖**。
- 数据库变更一律走 `supabase/migrations/` 增量文件（规范见 03-data-model §4）。
- 类型安全：新表生成 `src/types/database.ts` 类型，服务层禁止 `any`。
- 文档同步：需求变更 → docs/spec；技术方案 → tech-arch 文档，二者在里程碑 DoD 中检查。

**验收标准**
- [ ] 计划生成、回退计算、预警规则纯函数单测覆盖率 ≥ 90%（分支覆盖）；
- [ ] CI（或本地脚本）跑通：tsc + 单测 + 迁移 lint。

## NFR-6 可用性

- 核心按钮 ≥ 44px；快速记录入口在拇指热区（右下）；
- 空状态必有引导动作（去哪里、做什么）；
- 预警级别不依赖纯颜色传达：红/黄/绿须配图标与文字（色觉障碍友好）；
- 关键操作（删除记录、回退计划、注销）均有二次确认并明示后果。

**验收标准**
- [ ] 设计走查清单：44px、热区、空状态、色觉四项逐页核对；
- [ ] 所有破坏性操作清单化复查。

## NFR-7 可迁移性（平台解耦）`架构约束`

- **背景（v2.0-draft9 立项）**：后期将迁移至**自建数据库与自建认证**，Supabase 为过渡形态。自本条起，新增设计以「平滑迁移」为前置约束；目标库形态未定，因此约束落在「不加深专有依赖 + 授权收敛到应用层 + 数据模型可平迁」。
- **授权双裁决、应用层优先**：业务权限（数据可见性、角色权限点）的**主裁决点收敛在后端应用层**（FastAPI 统一鉴权依赖）；数据库 RLS 作为**纵深防御**保留于过渡期，判定口径与应用层一致——迁移后可整体关闭 RLS 而不改变任何可见行为。收敛点已存在：C 端全部数据流量唯一经过后端 `/v1` 通道，管理端新能力一律走 `/admin` API；
- **不新增 Supabase 专有依赖**：新增表/迁移一律普通 Postgres DDL，禁用 `auth.*` 引用、Supabase 专有函数，不新增 Edge Function；新增用户外键一律指向 `public.users`（**用户主数据**、身份事实源），不再新增对 `auth.users` 的引用；
- **身份与存储走适配层**：GoTrue 定位为过渡期认证适配器（C 端会话签发已收敛在后端 `/auth/*`）；文件存储沿用现有桶模式，新增存储需求经后端签发/代理，不新增客户端直连 Storage 的依赖；
- **存量不动（绞杀者模式）**：既有直连 PostgREST 的路径（admin 的 J2–J5、miniapp 数据通道）过渡期保持现状，迁移窗口统一收口为后端 API，避免双线重构。

**验收标准**
- [ ] 新增迁移文件不出现 `auth.` 引用与 Supabase 专有语法（迁移 lint 检查，并入 NFR-5 的迁移 lint）；
- [ ] 应用层与 RLS 判定一致性有自动化用例：同一越权请求经两条路径结果一致；
- [ ] 演练环境关闭 RLS 跑通核心链路（记录/家庭共享/管理端 API），行为与开启时一致；
- [ ] 新增管理端能力全部经 `/admin` API、新增表外键全部指向 `public.users`（code review 清单核对）。
