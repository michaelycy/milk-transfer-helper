## 1. 模块定位

账户层解决"数据跟着人走"：匿名登录（现状）换手机数据即丢，与宝妈换机/多设备的真实场景冲突。方向：匿名可用的前提下提供微信登录升级，并在升级时无损迁移数据。FR-H0 是全局阻塞项——不修复页面层与认证层的断裂，任何需求都无法在真机验证。

v2.0-draft8 起账户层延伸为两条线：**个人账户完善**（真实资料读写、个人中心死入口治理、隐私同意留痕、手机号绑定——FR-H2/H6/H7）与**多监护人协作**（家庭共享的成员角色权限——FR-H3），共同回答「用户是谁、谁能动哪些数据」这一底座问题。

### FR-H1 微信登录与数据迁移 `P0`｜依赖：H0｜闭环：全部
- 描述：微信授权登录替换纯匿名会话（`users.openid` 字段已预留）；老匿名用户升级登录时，其记录/收藏等数据**无损迁移**到正式账号。可行性说明：Supabase 无原生微信登录，采用 Edge Function 以 code 换 openid 并签发会话，技术方案在技术文档中细化。
- 验收标准：
  - [ ] 同一微信号重复登录为同一账号；
  - [ ] 匿名→微信升级后旧数据完整可访问；
  - [ ] 迁移幂等可重试，失败不产生重复数据；
  - [ ] 拒绝授权用户仍可匿名使用（明确提示数据不跨设备）。

  - [ ] 建档前单独同意留痕（与 FR-A1 联动）。

### FR-H3 家庭共享（成员与角色权限） `P2`｜依赖：H1、A2｜闭环：L1
> v2.0-draft8 由 P3 意图升级为详细设计（原「M2 后调研 ≥30% 再评估」的前置判断被多人记录诉求取代，里程碑 M4 内已列项）。

- 描述：爸爸/奶奶等以受控角色加入宝宝档案，共同记录与查看：
  - **成员角色与权限矩阵**（收藏、埋点、AI 会话等个人数据不共享，仍各自 own-policy）：

    | 操作 | owner | editor | viewer |
    |---|---|---|---|
    | 查看宝宝数据（记录/打卡/体重/计划/预警/统计） | ✓ | ✓ | ✓ |
    | 写记录/打卡/体重、管理计划、处理预警 | ✓ | ✓ | ✗ |
    | 使用 AI（消耗本人额度） | ✓ | ✓ | ✓ |
    | 编辑/删除宝宝档案 | ✓ | ✗ | ✗ |
    | 邀请/调整角色/移除成员 | ✓ | ✗ | ✗ |
    | 自行退出共享 | ✗（所有权转移本期不做） | ✓ | ✓ |

  - **邀请机制**：owner 生成 24 小时有效的**一次性**邀请短码（指定 editor/viewer 角色），经微信分享卡片送达；短码高熵随机不可枚举、验证失败限速，接受/过期/撤销任一发生后立即失效；被邀请人须为已登录正式账号（游客不可参与）；每宝宝 active 成员 ≤ 5；
  - **退出与移除**：非 owner 成员可自行退出；owner 移除成员须二次确认。退出/移除即时生效（该成员下一次请求即失访问）；其历史记录保留在宝宝时间线（记录人 `user_id` 保留），身份展示降级为「家庭成员」，不再披露其个人信息；
  - **权限裁决（双裁决，应用层优先）**：成员可见性由**后端 `/v1` 通道主裁决**（C 端全部数据流量本就唯一经过该通道），过渡期在既有 own-policy 上**同步追加 RLS 成员可见性策略**作为纵深防御（读 = owner 或成员，写 = owner/editor），两套口径一致（NFR-7）；存量用户由迁移自动补 owner 行，行为无感知；
  - **最小披露**：跨成员展示记录人仅限昵称/头像最小字段，经专用只读通道（视图/RPC）披露，不放宽 `users` 表整体读权限（03 §2.9）；
  - **入口**：宝宝档案页内「家庭共享」管理页（成员列表 / 邀请 / 调整角色 / 移除）；被邀请人经分享卡片进入接受页。
- 验收标准：
  - [ ] owner 邀请（editor/viewer）→ 被邀请人接受后出现在成员列表；短码一次性（接受/过期/撤销后即失效），连续验证失败触发限速；
  - [ ] viewer 真机只读：可查看记录/计划/预警，无任何写入入口，直连接口写入被 RLS 拒绝；
  - [ ] editor 可写全部记录类数据，但无成员管理入口；
  - [ ] 仅 owner 可调整角色与移除成员；owner 自身不可被移除或降级（所有权转移本期不做）；
  - [ ] 非 owner 成员自行退出后立即失去访问；退出后其历史记录保留且个人信息不再披露；
  - [ ] owner 删除宝宝档案前二次确认并明示「全部共享成员将同步失去访问」（NFR-6）；
  - [ ] 成员个人数据（收藏/埋点/AI 会话）互不可见；成员间仅可见昵称/头像，读不到彼此 `users` 全字段（含手机号）；AI 限额按成员各自 user_id 计；
  - [ ] 游客（匿名会话）不可发起或接受邀请；
  - [ ] 匿名→微信升级后成员与邀请关系无损（后端迁移白名单覆盖 `baby_members`/`family_invites`）；
  - [ ] 迁移附带越权回归自测：存量 own-policy 行为不回退，全部越权访问被拒。

### FR-H4 埋点与分析基建 `P0`（M1）｜依赖：H0｜闭环：全部（指标地基）
- 描述：统一事件模型与采集，是 glossary §5 全部指标的唯一数据源：事件表 `analytics_events`（03 §1），事件清单与指标公式见 [00-glossary.md](../00-glossary.md) §5（含 `app_launch(scene, first)`、`plan_created`、`feed_recorded(source, dur_ms)`、`alert_shown/alert_acked`、`share_card_created` 等 15 个事件）。初期以 Supabase 视图/仪表盘出数，不自建 BI。上报为 fire-and-forget：失败静默降级、不自动重试、不阻塞任何业务操作（可接受少量丢失）。
- 验收标准：
  - [ ] glossary §5 全部指标可由 `analytics_events` 表计算；
  - [ ] 分享（`scene=share_plan`）与问卷入口的归因参数落地到 `app_launch`；
  - [ ] 上报失败不影响主流程（弱网下无感）；
  - [ ] 事件仅可插入本人数据（无客户端 select 权限），看板走服务端角色（03 §2）。

### FR-H5 开屏页与全局未登录态 `P0`｜依赖：H1｜闭环：全部
- 描述：小程序启动先进入开屏页（品牌展示，停留 ≤1.5s 自动路由：已登录直达首页，未登录进入登录页）；四个 Tab 页在未登录态展示统一的「登录门」引导，不触发任何数据请求。登录页提供微信一键登录（走 FR-H1 Edge Function）与游客模式（匿名会话）兜底，《隐私政策》勾选为登录前置条件。
- 验收标准：
  - [ ] 已登录用户经开屏页无感直达首页（会话静默恢复，失败降级登录页）；
  - [ ] 未登录访问任何 Tab 页均展示登录引导，且不产生任何 Supabase 请求；
  - [ ] 隐私勾选为登录/游客入口的前置条件（留痕口径与 FR-A1/H2 一致）；
  - [ ] 游客模式入口明确提示「数据仅保存在本设备」（FR-H1 验收联动）；
  - [ ] 微信登录失败（Edge Function 未配置）时提示降级路径，不阻塞游客使用；
  - [ ] 埋点：`app_launch(scene)`、`login_success(mode)` 可统计（FR-H4）。

### FR-H6 用户资料与个人中心完善 `P1`｜依赖：H1｜闭环：全部（体验底座）
- 描述：让「我的」页从写死的占位变成真实账户中心：
  - **资料管理**：头像与昵称读写 `users.nickname/avatar`，采用微信官方「头像昵称填写能力」（`open-type=chooseAvatar` 按钮 + `type=nickname` 输入框，无强制授权弹窗，符合平台审核规范）；头像上传后存 URL，昵称 ≤ 20 字；
  - **游客态呈现**：未升级微信登录的会话显示「游客」标识与升级登录引导（含「数据不跨设备」提示，与 FR-H1 口径一致）；
  - **死入口治理**：profile 页「我的收藏」（已收藏文章列表，走 `favorites` 既有数据通道）、「设置」（聚合：资料编辑、隐私中心（FR-H2）、关于我们、退出登录）、「关于我们」（版本号、用户协议/隐私政策全文页、反馈邮箱）三类入口全部落地或移除，不允许存在点击无响应的入口；
  - **同意留痕**：登录页隐私勾选与建档单独同意写入 `privacy_consents`（FR-H2/H5 留痕口径统一落地）。
- 验收标准：
  - [ ] 昵称/头像修改后持久化，重进小程序仍生效；头像上传失败降级保留原头像；
  - [ ] 游客会话资料区显示游客标识，微信升级后切换为真实资料；
  - [ ] profile 页全部入口逐项点击核验有响应（收藏/设置/关于我们可用或已移除）；
  - [ ] 登录勾选/建档同意可在 `privacy_consents` 按用户查到（含协议版本号）；
  - [ ] 埋点：`profile_updated` 可统计（FR-H4）。

### FR-H7 手机号绑定与账号安全 `P2`｜依赖：H6、H1｜闭环：合规（NFR-2）
- 描述：微信手机号快捷绑定作为账号安全补充（**不是**登录方式切换）：「账号与安全」页内经 `open-type=getPhoneNumber` 授权 → 后端以 code 换手机号 → 加密存储 + 哈希指纹唯一（展示一律脱敏 `138****5678`）；支持换绑与解绑；绑定/换绑前弹**单独同意**并留痕 `privacy_consents(consent_type=phone)`。仅正式微信账号可绑定（游客先升级登录）；手机号用途限定为账号安全与找回，**不做营销触达**（02-roadmap 不做清单）。
- 验收标准：
  - [ ] 绑定成功后「账号与安全」页仅展示脱敏号；任何页面/接口不回传完整手机号；
  - [ ] 同一手机号不可被两个账号绑定（指纹唯一约束，冲突时明确提示）；
  - [ ] 换绑须重新授权确认；解绑后指纹与密文同步清除；
  - [ ] 单独同意未勾选时无法发起绑定（留痕含协议版本号）；
  - [ ] 后端数据库不存明文手机号（How 见技术文档，约束：密文 + 指纹双字段，03 §2.11）。
